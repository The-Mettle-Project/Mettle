The pipeline

Inside the compiler

Every stage below can be asked what it did. That is the point of this compiler: the diagnostics and the optimization report are not decoration on top of the pipeline, they are the pipeline explaining itself.

  ▼

  ▼

  │  semantic         src/semantic     types, borrows, memory, comptime

  ▼

Everything runs in one process. There is no external assembler, no assembly text anywhere in the pipeline, and no LLVM.

Lexer

src/lexersource → tokens

Keywords resolve through two length-bucketed sorted tables: language keywords matched exactly, inline-assembly mnemonics and register names matched case-insensitively. A binary search within one length bucket settles a lookup in a few comparisons, which matters because most identifiers are not keywords. Identifiers are interned, so later phases compare pointers rather than strings.

Reports: E0001 when a byte cannot become a token.

Parser

src/parsertokens → AST

Recursive descent. Error recovery resynchronizes at block boundaries, so one missing brace reports once rather than cascading — which is why a Mettle syntax error is usually one diagnostic and not a page of them.

Reports: E0002.

Semantic analysis

src/semanticAST → checked AST

Types, scopes, traits, comptime expansion, and the analyses that make this stage the loudest in the compiler: the borrow checker, the memory diagnostics, and the range checks. They run at compile time on code that is otherwise legal, which is why most of what they print are warnings.

Reports: E0003, E0004, E0005, and the whole M0101–M0119 range — use after free, double free, stack addresses that escape, leaks, borrowed pointers invalidated by realloc or free, null and out-of-bounds access, shift and divide constants, loop indexes that run past the end, and narrowing conversions.

IR lowering

src/irchecked AST → IR

A function becomes a list of named-value instructions with labels and branches. Types are attached to instructions, so code generation never re-derives one. This is also the seam another frontend would enter through: everything below here is libmtlc and knows nothing about Mettle's syntax.

See it: --emit-ir, and --dump-ast for the stage before.

Optimizer

src/ir/optimizerIR → optimized IR

Around forty passes. The shape is: loop canonical form first, because every recognizer behind it assumes that form; then the core simplifications to a fixpoint — copy and constant propagation, CSE, branch simplification, reassociation, dead write elimination, jump threading; then a recognizer worklist; then a tail of lowering cleanups.

A convergence check fails the build when the fixpoint does not settle, so a pair of passes that undo each other is caught rather than spun on.

Reports: every decision code — the 24 reasons a loop did not vectorize, the 15 reasons a call was not inlined, and the 11 things the optimizer applied. This is what --explain prints.

Code generation

src/codegenIR → machine code

Four targets and one shared object writer. On x86-64 there are two backends and most functions take the first: MIR, a machine-level IR with real register allocation — Chaitin-Briggs graph colouring by default, over the full general set plus xmm0–15, with R10 and R11 held back as scratch.

When MIR cannot take a function, it falls back to a spill-everything backend that keeps every value on the stack. The backend report names which functions fell back and why, because that fallback is the single largest thing that can quietly cost you performance.

See it: --annotate-asm for per-instruction provenance, --profile-blocks for a block profile.

Linker

src/linkerobjects → executable

A complete PE linker of its own, plus ELF reading. Its distinctive rule is that runtime objects' symbols are overridable defaults, so a program defining strlen replaces the runtime's without a duplicate-symbol error, while the runtime keeps calling its own. Link-time section collection drops what nothing reaches.

Reports: E0006 for I/O.

The interpreter, and why it matters here

src/ir/ir_interp.c executes IR with a real memory model: strings with their bytes, structs, arrays, globals, heap allocation, closures. Four features run on it, and two of them are the reason the report can make the claims it does.

mettle test

Runs @test functions with no code generation at all.

mettle trace

Prints a function's values line by line.

--pgo

Interprets main() at compile time and counts calls, so layout and inlining decisions have real frequencies without a profiling run.

--verify

Executes each function before and after every pass and compares. A pass that diverges is quarantined for that function and the build continues from validated IR.

Why the report can say "proven"

The same machinery is what lets --explain apply a suggested fix to a clone of your function, re-run the optimizer on it, and report what actually happened — rather than guessing that the advice would work.
